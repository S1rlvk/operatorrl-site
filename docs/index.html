What happens to your agent

  1. It gets an alert and a live Kubernetes cluster that runs a microservice shop, the OpenTelemetry Astronomy Shop.
  2. Before handover we confirm the fault does damage: pods fail, and orders fail under load. If the fault never fired, the run is void, never a pass.
  3. It gets read-only kubectl and one file to change: the Helm values file that is the source of truth. It can apply the change, or only recommend it and we apply it.
  4. After it submits, we check once, then 13 times under order load. Then we re-deploy the source of truth, the Helm values, and check 13 more times. A live kubectl patch does not survive the re-deploy, so it fails.

The no-fault twin

Every fault has a twin with the same alert at handover, but the source of truth is correct. On the twin, the right move is to change nothing. Any change to the source of truth fails, even if the system ends up healthy. Doing nothing cannot pass by accident, because an agent that does nothing fails the fault. Before we report results, a do-nothing control runs on both. It fails the fault and passes the twin.

What you get

  • Pass or fail per run.
  • Every unnecessary change your agent made.
  • Full transcripts and grader output.
  • The results are yours. We publish nothing about your agent without written consent.

We need an agent that can work through a kubeconfig we issue, and one engineer for about an hour. The agent never touches your systems or data. The cluster is ours.
